# Architecture

## Layers

```
            +-------------------------------------------------------+
 Layer B    | cli/ (native Fe executable)                            |
            |   argument parsing, printing, file I/O                 |
            |   uses (out: mut Stdout, args: Args, fs: mut Fs)       |
            +--------------------------+----------------------------+
                                       |
            +--------------------------v----------------------------+
 Layer A    | ingots/fecheck (pure Fe, no effects of its own)        |
            |                                                        |
            |  rng ---> source ---> gen                              |
            |              |                                         |
            |              v                                         |
            |   runner (check) <---> shrink                          |
            |              |                                         |
            |   machine (StateMachine, traces)                       |
            |              |                                         |
            |   artifact (.case encode/decode) ---> replay           |
            |   json (export)                                        |
            +--------------------------------------------------------+
                     ^                    ^                   ^
           examples/permissions   examples/queue    examples/contract
           (library SUT)          (library SUT)     (EVM contract SUT via
                                                     the Evm effect)
```

Layer C (a trace viewer) was optional and is not built; the CLI prints the
same information and `--json` exports it for any external viewer.

## The central idea: tests read a choice sequence

A FeCheck test is any callable `F: Fn(mut Source) -> Verdict`. Generators do
not receive random numbers; they ask the `Source` for bounded *choices*
(`draw(max) -> 0..=max`). In random mode the source draws from SplitMix64 and
records every choice. In replay mode it hands back a recorded list, clamping
out-of-range values and returning 0 past the end.

This is the design Hypothesis calls internal reduction (MacIver & Donaldson,
"Test-Case Reduction via Test-Case Generation", ECOOP 2020). FeCheck adopts it
because it fits Fe unusually well:

* **No generic shrinkers.** Fe has no trait objects or reflection, and a
  per-type shrinker for every generic value would be a lot of trait plumbing.
  The shrinker only edits a `MemVec<u64>`, so one shrinker serves integers,
  lists, pairs, user generators and state machines.
* **Shrunk inputs are always valid.** Every candidate is regenerated by the
  real generator and the real `gen_cmd`, which sees the real model state, so
  a shrunk command sequence can never contain a command the generator could
  not have produced. Preconditions are re-evaluated on every candidate.
* **Replay needs no serialization of Fe values.** A case file stores integers
  plus the rendered operations for humans and for drift detection.

### Encoding conventions

* Smaller choices mean simpler values: `uint_in(lo, hi)` is `lo + choice`;
  `int_in` zig-zags around 0 (0, +1, -1, +2, ...); command kinds are ordered
  simplest first.
* Lists and command sequences put a "more" flag before each element, so
  deleting an element's choices deletes exactly that element and lowering a
  flag to 0 truncates the list.

## Engine

`check(test, config)`:

1. For case `i`, seed a fresh source with `case_seed(seed, i)` (SplitMix64's
   mixer applied to seed and index), so any case can be regenerated alone.
2. Run the test. A case that overruns `max_choices` is discarded; too many
   discards end the run as `GaveUp`.
3. On the first `Fail` or `Error`, shrink and return `Failed` with the
   original and shrunk choices and statistics.

`shrink` repeats three passes until a round makes no progress or the budget
of candidate evaluations is spent:

1. delete runs of 8, 7, ..., 1 consecutive choices;
2. lower each choice: try 0, then binary-search the smallest failing value;
3. lower adjacent pairs together.

A candidate is adopted only if (a) it fails with the same verdict kind and
code and (b) the choices it actually read are strictly smaller in shortlex
order. (b) guarantees termination; (a) stops the shrinker from sliding from
one bug to a different, easier one. The result is a *locally minimal*
counterexample, not a global minimum.

## State machines

`StateMachine` has associated types `Cmd`, `Obs`, `Model`, `Sut` and methods
for creation, generation, preconditions, model and SUT transitions, an
invariant and failure descriptions. `run_steps` executes one generated
sequence; `run_traced` does the same and records every step (command, skip,
expected and actual observation, verdict). Per command:

1. read the "more" flag; stop at 0 or at `steps.max`;
2. `gen_cmd(src, model)`;
3. if the precondition fails, record a skip and continue (identically in
   generation, shrinking and replay);
4. apply to model and SUT, check the invariant, then compare observations.

The invariant is checked before the postcondition so that the named property
(`revoked_agent_cannot_execute`) is reported rather than a bare mismatch.

Every run starts from `new_model()` and `new_sut()`. Contracts (Demo C) get a
fresh deployment per run via `evm.create`.

## Replay and artifacts

`.case` files are line-oriented, versioned text (schema 2, see
`artifact.fe`; schema 1 is still read). They carry the shrunk choices (the
replay input), the generation settings (`steps <max> <mean>`), provenance
(seed, case index, compiler) and the expected outcome (verdict, failed step,
rendered ops, violation). Replay runs with the recorded settings and checks
the whole recorded trace: exactly as many operations as recorded, each
identical, every recorded choice read. Then it classifies the result as:

| Outcome | Meaning | CLI exit |
|---|---|---|
| `Reproduced` | same verdict kind, code and step | 0 |
| `NoLongerFails` | the same operations now pass | 3 |
| `DifferentFailure` | fails, but not as recorded | 5 |
| `Invalid` | the choices no longer form a valid case | 4 |
| `Drift` | regenerated trace differs from the recorded one (an op changed, missing or extra; choices left unread) | 4 |

The parser treats files as untrusted: bounded file, line and choice counts,
strict key order, decimal-only u64 parsing with overflow checks, mandatory
`end`, no trailing data. Malformed input returns a `ParseError`, never a
panic and never a pass.

## Effects as a design tool

* `ingots/fecheck` declares no effects anywhere. The compiler therefore
  guarantees that no generator, shrinker or replay can read the clock, the
  filesystem, the environment or host randomness: determinism is enforced by
  the type system, not by convention.
* The engine is generic over the test's effects (`uses F::E`). The same
  `check` and `shrink` drive a pure library (Demos A/B) and a deployed EVM
  contract (Demo C, `uses (evm: mut Evm)`), with no adapter layer.
* Only `cli/` declares `Stdout`, `Args` and `Fs`, so I/O is confined to one
  file.

## Comparison with existing tools

| Tool | What it already does well | How FeCheck relates |
|---|---|---|
| Hypothesis (Python) | Choice-sequence generation and internal shrinking, stateful testing, example database | FeCheck re-implements the core choice-sequence idea in Fe at a much smaller scale (no coverage guidance, no example database, simpler passes). |
| proptest (Rust) | Value trees with per-strategy shrinking, persisted failure seeds, state-machine testing crate | FeCheck shrinks choices instead of value trees, and persists the shrunk input, not a seed. |
| fast-check (JS/TS) | Arbitraries, model-based testing, replay by seed and path | Similar model-based API shape; FeCheck's replay file carries the input itself plus drift detection. |
| Foundry (forge fuzz / invariant) | Fuzzing and invariant testing of compiled EVM bytecode, call-sequence shrinking, huge ecosystem | Fe projects can already be fuzzed through Foundry on bytecode. FeCheck works at the source level inside `fe test`, also covers native Fe code, and lets the model be written in Fe. It is far less mature and does not replace Foundry. |
| Echidna | Grammar-free property fuzzing of EVM contracts with coverage guidance, sequence shrinking | Echidna is coverage-guided and much stronger at finding deep contract bugs; FeCheck has no coverage feedback. |

A public search on 2026-11-18 found no other Fe-native property-testing
library; [argotorg/fe#1387](https://github.com/argotorg/fe/issues/1387)
asks for fuzz testing, and existing Fe repositories such as `fe-lang/rosetta`
fuzz Fe bytecode through Foundry. We do not claim FeCheck is the first such
tool, only that we could not find another.
